## §1 · 画布

**16:9，1280 × 720 设计像素。**

选 1280×720 而不是 1920×1080 的理由，是导出 PDF 时能做到 1:1 无缩放：

```
1280px ÷ 96dpi = 13.333in = 960pt
 720px ÷ 96dpi =  7.500in = 540pt
```

1280 在 96dpi 下正好等于 13.333in，所以屏幕渲染和纸张逐像素对应，不会有半像素的模糊。

## §2 · 基准单位 `u`

> **只看屏幕共享场景（在线会议软件共享屏幕）。投影那套已作废。**

### 为什么两个场景推出来的东西不一样

| | 投影 | 屏幕共享 |
|---|---|---|
| 观众在哪 | 8 m 外 | **0.6 m**（自己屏幕前） |
| 画面大小 | 固定（幕布多大就多大） | **对方窗口多大就多大** |
| 信号链 | 光学 | **视频编码 + 网络** |
| 黑位 | 差（发灰） | 正常 |
| **会坏的东西** | 字号太小 | **1px 的细节** |

视觉标准是同一条（字符高度 ≥ **20 弧分**），但 `d` 和像素密度完全变了。

### 推导

屏幕共享下，观众看到的是**缩放后**的画面。设：

- `d` = 观看距离 ≈ 0.6 m
- `ρ` = 观众屏幕像素密度 ≈ 5 px/mm（13" 1440px 笔记本）
- `Sv` = **幻灯片在对方屏幕上的显示宽度**（CSS px）

20 弧分在 0.6m 处的物理高度 = `600 × tan(0.333°) = 3.49 mm`，即屏幕上 **17.5 px**。

幻灯片按 `Sv/1280` 缩放，所以：

```
u = 17.5 × 1280 / Sv = 22400 / Sv
```

| 对方的显示宽度 `Sv` | 场景 | `u` 下限 |
|---|---|---|
| 1920 | 全屏看 1080p 共享 | 11.7px |
| 1440 | 13" 笔记本全屏 | 15.6px |
| 1280 | 窗口刚好 1:1 | 17.5px |
| 960 | 半屏窗口 | 23.3px |
| 900 | 初版取这里 | 24.9 → 25px |
| **800** | **现在取这里** | **28px ← 设计上限** |
| 720 | 小窗口 | 31.1px |

**取 `Sv = 800px` 作为要支持的最窄窗口 → `u = 28px`（现在用的值）。**

推导表里 900px 那一档算出的是 25px —— 那是初版。后来取 800px，理由有两层：

1. **同一份 deck 往往还会被当 PDF 发出去**（手机上、别人电脑上），那边 `u` 越大越好
2. 但 `u` 有硬上限（见下），**28px 已经是天花板** —— 再大骨架就吃掉整页

所以 `u = 28px` 是「尽量大，但不超过设计上限」的结果，不是从 800px 反推出来的巧合。

> **与投影公式的关键区别**：投影时 `u` 由场地物理尺寸决定，你控制不了；屏幕共享下由**对方窗口宽度**决定，而那是你可以选的“要支持到多窄”的工程参数。

**`u` 同时是正文的字号、字号的基准、和所有间距的倍数。**

### ⚠️ `u` 不是可以随便调的——实测适用区间

初版设计时我以为"改 `u` 一个数，整套等比缩放"就够了。**实测证明这是错的**：
骨架（页眉 / 标题 / 导语 / 落点句 / 页脚）也随 `u` 线性增长，`u` 一大，骨架自己就把整页吃光。

实测（`./scripts/check.py` 扫各档 `u`）：

| `u` | 正文区 | 骨架占用 | 骨架占比 | 条目表(含注) | (无注) | 三条论点 | 判定 |
|---|---|---|---|---|---|---|---|
| 19px | 405.9 | 314.1 | 43.6% | 7 行 | 9 行 | 7 条 | ✓ 舒适 |
| 22px | 357.4 | 362.6 | 50.4% | 5 行 | 7 行 | 5 条 | ✓ 舒适 |
| 25px | 309.0 | 411.0 | 57.1% | 4 行 | 5 行 | 4 条 | ✓ 舒适（初版默认） |
| **28px** | **259.6** | **460.4** | **63.9%** | **3 行** | **4 行** | **3 条** | **✓ 可用（现在用的值）** |
| 31px | 211.1 | 508.9 | 70.7% | 2 行 | 3 行 | 2 条 | △ 很挤 |
| 34px | 161.7 | 558.3 | 77.5% | 1 行 | 2 行 | 1 条 | △ 很挤 |
| 37px | 113.2 | 606.8 | 84.3% | 1 行 | 1 行 | 1 条 | ✗ 崩溃 |

**设计上限 `u ≤ 28px`。** 超过这个值，骨架占比突破 64%，正文区容不下一个完整的原型，格式开始失效。真需要更大的字（礼堂、户外），要换的不是 `u`，是**骨架本身**——砍掉导语，再砍掉落点句。

### 场地对照表已作废，改用「最窄窗口宽度」

| 要支持到多窄的窗口 `Sv` | 取 `u` | 对应场景 |
|---|---|---|
| 1280px | 17px | 只在窗口最大化时看 |
| 1024px | 22px | 一般窗口 |
| 900px | 25px | 初版默认 |
| **800px** | **28px** | **现在的值（保守档）** |
| 720px | 31px | 很保守（骨架已经吃掉 71%） |

**`u` 越大，能放的内容越少**——“保守”不是免费的。上表右侧几档的代价是真的大。

## §2.5 · 字体必须内联（实测出来的硬结论）

**不要用系统字体。** 三个理由，第三个是决定性的。

### ① 装没装

`Calibri` 只存在于 Office 的 app 包里，**没有注册到系统** —— Chrome 看不见它。
用 JS 实测：`font-family:Calibri` 与 `font-family:NoSuchFontXYZ123` 渲染结果**字节级相同**。
思源黑体 / Noto Sans SC 在 macOS 上**完全没有**（系统中文是 PingFang）。

所以「用 Calibri」这句话，在没内联之前，实际效果是「用回退字体」。

### ② 换行

字体变了，同样的文案会在不同位置折行。**余量测量只有字体锁死才有意义。**
内联之后，`check.py` 量到的换行就是最终的换行。

### ③ PDF 的 Type 3 —— 决定性的一条

| 字体来源 | PDF 里的类型 |
|---|---|
| 系统字体（PingFang 等可变字体实例） | **Type 3** —— Skia 逐字形发矢量指令 |
| 内联的静态字体（子集） | **CID TrueType + Identity-H + 子集** |

实测同一份 9 页 deck：

| | 内联前 | 内联后 |
|---|---|---|
| Type 3 字体数 | **146** | **0** |
| 字体条目 | 152 | 4 |
| PDF 大小 | 504 KB | **114 KB** |

**这直接解决了原来「PingFang 只能导成 Type 3」的死结** —— 不需要换字体，只需要把字体**变成静态的并内联**。

### ④ 打印时必须隐藏所有 UI

**踩过的坑**：调参按钮是 `position:fixed`，会被打进 PDF。
它用的是 `font:600 .. "PingFang SC"` → 3 个 Type 3 又回来了。

不要列举 `#notes,#help,.chrome` 之类的名字 —— **以后再加任何 UI 都会漏**。
用一条通用规则：

```css
@media print{ body>*:not(#stage){display:none!important} }
```

### ④ 改完文字必须重跑 build_font.py

**踩过的坑**：字体内联之后又改了展示页的文案，新加的字（`剩`、`无`）不在子集里
→ 静默掉回 PingFang → PDF 里冒出 Type 3。**屏幕上完全看不出来**，因为回退字体长得差不多。

`check.py` 现在会机械检查这件事：

```
字体检查：内联 2 个子集（SlideNotoSC），覆盖 399 个码位
  ✗ 有 2 个字符不在子集里：
      剩无
  → 这些字会掉回系统字体（屏幕上可能看不出来），PDF 里会变成 Type 3。
```

`build_font.py` 是幂等的（会先把旧 `@font-face` 剥掉），所以**改完文字直接重跑就行**。
Type 3 数量不为 0 时 `check.py` 现在直接判失败，不再只是打印一行。

### 怎么做

```bash
python3 -m pip install fonttools brotli
./scripts/build_font.py deck.html          # 原地内联
./scripts/build_font.py deck.html --report # 只看大小
```

`build_font.py` 会：实例化 Noto Sans SC 变量字体到 400/700 → 按 deck 里**真实出现的字符**子集化 → WOFF2 → base64 内联。

实测代价（9 页中文 deck，386 个字符）：

| 字体 | WOFF2 子集 |
|---|---|
| 思源黑体 Regular | 135.8 KB |
| 思源黑体 Bold | 136.6 KB |
| Calibri Regular | 127.0 KB |
| Calibri Bold | 112.6 KB |
| **合计** | **683 KB** |

> 16.9 MB 的变量字体 → 136 KB。**子集化是必须的，不是优化。**

### 版权

| 字体 | 许可 | 能否内联分发 |
|---|---|---|
| 思源黑体 / Noto Sans SC | SIL OFL | ✓ 可以 |
| Calibri | Microsoft（随 Office 授权） | △ 内部用途可以，对外分发要换成 Carlito（OFL，度量兼容） |

### 决定：拉丁也用思源黑体（`--latin noto`）

**不用第二套拉丁字体。** 思源黑体自带一套 Source Sans 血统的拉丁（`g` 单层带开口尾、
`a` 双层、`R` 直腿），Adobe 造它就是为了和汉字配。

实测过五套方案，选它的理由**没有一个是审美**：

| | 拉丁 | 字重齐平 | 拉丁宽度 | 许可 | HTML | PDF |
|---|---|---|---|---|---|---|
| **✓ 纯思源** | 无 | **完美** | 763.9 | **OFL** | **400 KB** | **85 KB** |
| Arimo | Arimo | 偏重 | 691.0 | OFL | 431 KB | 89 KB |
| Helvetica | Helvetica | 偏重 | 691.0 | Apple | 469 KB | 100 KB |
| Calibri | Calibri | 偏轻 | 窄 | Microsoft | 720 KB | 114 KB |
| 混合 | Helv 标题 | 标题偏重 | 691.0 | Apple | 469 KB | 98 KB |

1. **唯一解决「字重不齐」的方案**，而且是设计时解决的，不是靠调参凑的
2. **OFL** —— 发给客户没有授权问题（Helvetica/Calibri 都有）
3. **一个字体家族 = 一个失败模式**（字体相关的 bug 我们已经踩了三个）
4. **最小**

**唯一要认的代价**：思源的拉丁比 Helvetica **宽 10.5%**（763.9 vs 691.0 px @48px）。
同样 58px、同一栏宽实测：

| | 第一行装下 |
|---|---|
| Helvetica | `Projector vs. screen` · `What actually holds` |
| 思源黑体 | `Projector vs.` · `What actually` |

**英文标题可能多占一行 → `--fs-h1` 一行 = 67px**，而最紧的页只剩 56px 余量。

> **这个风险是 `check.py` 机械抓的**，不是隐藏的。真溢出就把标题改短一个词。
> 如果哪天要换回窄拉丁，`build_font.py --latin arimo` 一条命令即可（Arimo 与 Helvetica 度量完全相同）。

## §3 · 字号

**等比数列，公比 1.2，基准 `u`。**

```css
--fs-cover:  calc(var(--u) * 3.00);    /* n=+6 */
--fs-h1:     calc(var(--u) * 2.07);    /* n=+4 */
--fs-quote:  calc(var(--u) * 1.44);    /* n=+2 */
--fs-lead:   calc(var(--u) * 1.20);    /* n=+1 */
--fs-key:    calc(var(--u) * 1.20);    /* n=+1 */
--fs-body:   var(--u);                 /* n= 0  ← 下限 */
--fs-note:   calc(var(--u) * 0.83);    /* n=-1 */
--fs-kicker: calc(var(--u) * 0.69);    /* n=-2 */
--fs-foot:   calc(var(--u) * 0.58);    /* n=-3 */
```

`u = 25px` 时：

| 档位 | 值 | 角色 |
|---|---|---|
| cover | 75px | 封面主标题 |
| h1 | 52px | 页面主标题（英文衬线） |
| quote | 36px | 落点句 |
| lead / key | 30px | 导语 / 条目表关键词 |
| **body** | **25px** | **正文 —— 下限** |
| note | 21px | 注解、代价说明 |
| kicker | 17px | 小节标签 |
| foot | 14px | 页脚、页码 |

倍数是 `1.2ⁿ` 推出来的。`52px` 不是"上次用了 54"，而是 `25 × 1.2⁴`。

### ⚠️ 字号只能用阶梯上的值

**阶梯之外的中间值一律不许出现。** 曾经在下标里散落着 `0.84u` / `0.76u` / `0.64u` / `0.6u` / `0.52u` / `0.48u` 六个自造值——那等于绕过了整套字号系统：改 `u` 的时候它们不跟着变。

代码里凡出现 `font-size:`，右边必须是 `var(--fs-*)`。

### 三级字号纪律

| 级别 | 令牌 | u=25 | 装什么 |
|---|---|---|---|
| **一级**（必须读） | `--fs-body` | 25px | 正文、条目表的说明、论点的文字 |
| **二级**（辅助） | `--fs-note` | 21px | 注解、代价说明、循环图的节点说明 |
| **三级**（索引/装饰） | `--fs-kicker` `--fs-foot` | 17 / 14px | 编号、小节标签、英文小注、页码 |

三级也承载信息，但**不承载独有的信息** —— 不看它也能跟上论证。

### 字体：两个栈

```css
--font-title: Georgia, "Times New Roman",
              "PingFang SC", "Hiragino Sans GB", "Microsoft YaHei",
              "Helvetica Neue", Arial, sans-serif;
--font-body:  "PingFang SC", "Hiragino Sans GB", "Microsoft YaHei",
              "Helvetica Neue", Arial, sans-serif;
```

- **标题栈的写法是「拉丁取衬线 → 中文回退到黑体」**，靠字体回退实现。
  名字不叫 `--serif` 就是因为**它并不纯是衬线**：只写 `serif` 会让 h1 里的中文静默变成宋体，违反下一条。
- **中文一律用黑体** —— 宋体类在小字号投影下发虚。

### ⚠️ 字体可移植性：PingFang SC 是 macOS 独有

实测（列宽 1100px / 30px 字号）：

| 文本 | PingFang | Hiragino Sans GB | STHeiti | Songti SC |
|---|---|---|---|---|
| **纯中文** | 1 行 | 1 行 | 1 行 | 1 行 |
| **中英混排** | **1 行** | **2 行** | **2 行** | 1 行 |

- **纯中文不受影响** —— CJK 字形在所有中文字体里都是 **1em 等宽**，而行高是写死的
- **中英混排会差 ±1 行** —— 拉丁部分的宽度因字体而异，挤动了中英边界的换行
- 一行导语 = `--fs-lead(1.2u) × --lh-body(1.6)` = **1.92u = 48px @ u=25**

**所以余量门槛是 48px，不是 8px**（见 §4）。低于这个值的页面，换台 Windows 机器讲就可能当场溢出。

**当前状态：未解决。** 三个选项，按成本排：

1. **声明「仅 macOS 放映」** —— 零成本，诚实
2. **内联字体子集** —— 解决问题，但破 §3.9 的单文件约束（子集几百 KB）
3. 让 `check.py` 用更保守的字体栈测量 —— 把余量门槛当作缓冲区（已这样做）

## §4 · 骨架与容量

### 六个锚点

只有 **④ 正文区**伸缩，其余五个位置恒定。

```
┌──────────────────────────────────────────────────┐
│ ① 页眉 · 小节标签 ＋ 分隔线             距顶 1.75u│
│ ② 主标题 h1                                      │
│ ③ 导语 lead（可选）                              │
│ ④ 正文区 —— 唯一伸缩的一块                       │
│ ⑤ 落点句（可选）        ← 永远贴在这里           │
│ ──────────────────────────────────────────────── │
│ ⑥ 页脚 · 左讲者 / 中 deck 全名 / 右页码 距底 1.25u│
└──────────────────────────────────────────────────┘
```

#### ⚠️ 页脚两个槽的语义是**固定**的，不要各填各的

| 槽 | 语义 | 每页 |
|---|---|---|
| **中** | **deck 全名** | 相同 |
| **右** | 页码 | 变化 |

**页脚 = 文档身份条。** 中间告诉读者「这是哪份」，右边告诉「到哪了」。
**小节位置由页眉的 `.kicker` 承担** —— 它就在顶上，页脚再写一遍是重复。

#### 讲者**只出现在封面** —— 本模板固定为 `Fengrui`

| 位置 | 值 | 出现频率 |
|---|---|---|
| 封面 `.ctag` | `主题标签 · Fengrui` | **唯一一处** |

**作者不上每页。** 每页都署名是冗余：读者翻到任何一页都知道这是哪份 deck，
而「谁做的」只需要在开头说一次。

**但封面必须有。** 一份 deck 会被**转发、被单独截图、被从中间某页开始看** ——
封面是唯一能注明出处的地方。不写，它就变成了**没有出处的匿名文件**。

> **`.ctag` 不要 `text-transform:uppercase`。** 原来是加了的，于是人名渲染成 `FENGRUI`。
> 人名不该被 shouting；而且它和页脚如果都出现，大小写就不一致。
> 现在 ctag 是 `Multi-Model Workflow · Fengrui` —— 标签保持原样，人名保持原样。

> **实测（这条规则改了两版才对）**：
>
> | 版本 | 页脚左槽 | 问题 |
> |---|---|---|
> | v1 | `<span>署名</span>` 占位 | **「署名」是什么都没说** |
> | v2 | Reviewer 填 `Jerry`· Agent 填 deck 名 | 同一个槽被填成两种东西 |
> | v3 | 统一 `Fengrui` | 作者上了每页 —— **冗余** |
> | **v4** | **删掉左槽** | ✓ |
>
> **占位符只写「署名」而不给值，等于没定义** —— 每个填的人都会猜得不一样。

> **这条是因为两份 deck 显得像两套模板才补上的。** 原来模板从未定义过页脚：
>
> | | 左 | 中 |
> |---|---|---|
> | Reviewer | `Jerry`（人） | **每页在变的副题** |
> | Agent | **deck 名** | deck 英文名（← 和左重复） |
>
> **两个错法还不一样。** 模板只写了 `<span>署名</span><span>Deck title</span>`，
> 剩下全靠填的人猜 —— 而每个填的人都会猜得不一样。
>
> **模板里没定义的槽，早晚会被填成三种不同的东西。**

### 实测容量（`u = 25px`）

| 页面组成 | 正文区高度 |
|---|---|
| 导语 ＋ 落点句（默认页） | **309.0px** |
| 只有落点句 | 372.0px |
| 都没有 | 435.0px |

**推导值和实测值差了 46px（约 15%）。** 手推 §4 得到 285px，实测是 309px——中间漏算了行高的舍入和边框。**这一条是这份规范里最值得记住的教训：推导给起点，实测给真相。**

### ⚠️ 静默重叠——这套骨架最危险的失效模式

`.body` 是 `flex:1`。**内容超量时它不会把页脚顶下去，而是让内容直接压在落点句上。**

已经踩过两次 —— 都在真实 deck 上。所以：

```css
.body{flex:1;min-height:0;overflow:hidden}
```

`overflow:hidden` 把它从「重叠」降级为「裁切」，但那仍然是**静默失败**。真正的防线是 `check.py`。

### 余量门槛 = 导语一行 = 1.92u

```
门槛 = --fs-lead(1.2u) × --lh-body(1.6) = 1.92u = 48px @ u=25
```

**为什么不是 8px：** 见 §3 的字体可移植性——中英混排在换字体时会差 ±1 行。余量不到一行，换台机器就溢出。

`check.py` 逐页测「正文区高度 − 内容实际伸到多深」，低于门槛就报警。`u` 未定义的 deck 只列数字不判死（门槛需要 `u` 才能算）。

### 越界怎么判：纵向严、横向松

| 方向 | 比什么 | 为什么 |
|---|---|---|
| **纵向** | `.body` 盒子 | 它下面紧跟着落点句和页脚，越界就是**碰撞** |
| **横向** | 幻灯片的**物理边缘** | 页边距是空白，色带向外渗是**有意的设计手法** |

依据：真实 deck 第 7 页的底色行用 `margin:0 -19px`，让带底色的行与上下行**文字对齐**；色带往 76px 的页边距里渗 19px 还剩 57px。按 `.body` 盒子判会误报成溢出。

### ⚠️ 改字号也要重测容量，不只是改 `u`

修「字号只能用阶梯上的值」那条时，英文小注从 `0.48u` 提到 `--fs-foot`(0.58u)，行变高，**条目表页的余量当场从 +12.1px 掉到 +0.1px**。

**容量是「字号 × 行高 × 行数」的函数，动任何一个都要重跑 `check.py`。**

## §5 · 颜色与线宽

### 硬约束一：对比度

屏幕共享不像投影仪那样黑位发灰，对比度要求可以放宽——**但下面那条线宽要求更硬**。

| 用途 | 门槛 |
|---|---|
| 正文文字 | **≥ 4.5:1** |
| 大号文字（≥1.44u）与图形 | **≥ 3:1** |
| 分隔线（除线宽要求外） | **≥ 2:1** |

### 硬约束二：屏幕上不许有 1px 的细节

**这一条是屏幕共享独有的，而且比对比度重要。**

H.264/VP8 用 8×8 DCT + 4:2:0 色度抽样。**一个像素宽的特征在量化中会被直接抹掉**，跟码率无关。

用 AVFoundation 做了真实的 H.264 往返（1280×720 → 960×540），实测对比度留存：

| 方案 | 原始 | 编码后 | **存活率** |
|---|---|---|---|
| **1px `#d0d0d0`（原设计）** | 18.4% | **0.8%** | **4%** ← 被摧毁 |
| 1px `#a8a8a8`（加深） | 34.1% | 5.5% | 16% |
| 2px `#c4c4c4` | 23.1% | 12.6% | 54% |
| **2px `#b8b8b8`（现用）** | 27.8% | **22.0%** | **79%** |
| 2px `#a8a8a8` | 34.1% | 26.7% | 78% |
| `#e8e8e8` 底带 | 9.0% | 7.5% | 83% |

**两条从数据里出来的规则：**

**① 线宽比对比度重要。**
`1px #a8a8a8`（原始对比度 34.1%）编码后只剩 5.5%；而 `2px #d0d0d0`（原始只有 18.4%，一半）编码后还有 9.4%。**加深一条 1px 线救不了它，加粗才行。**

**② 用面，不用线。**
1px 线存活 **4%**；2D 底带存活 **77~83%** —— **相差 20 倍**，即使底带的原始对比度低得多。代码杀掉的是“细线”（一个像素宽的 DCT 系数被量化没了），而**面状区域的平均亮度能保留**。

### 硬约束三：面必须能被**区分**出来

「用面不用线」只说了面比线好，**没说面之间怎么分层**。这一条是重建一份已有真实 deck 时实测出来的。

**4:2:0 抽样不只杀细线，它把色度一起降采样。** 后果是——

> **近白底色不是「变淡」，是螥成同一个中性灰。**

老 deck（8 页 Reviewer）的整套底色实测：

| 老底色 | 原始 rgb | 编码后 rgb | 结果 |
|---|---|---|---|
| `#fcfcfd` card | (252,252,253) | **(252,252,252)** | 色偏归零 |
| `#fbf9f8` band（**暖**） | (251,249,248) | **(252,252,252)** | **与 card 完全相同** |
| `#fbfbfc` strip | (251,251,252) | **(252,252,252)** | 同上 |
| `#fbf6f3` 强调行（**暖**） | (251,246,243) | (247,247,247) | 色偏归零 |
| `#f1f3f6` code（**冷蓝**） | (241,243,246) | (246,246,246) | 色偏归零 |
| **`#f5dfe0` accent-bg** | (245,223,224) | (249,227,231) | **86% 色偏保留 ✓** |

**四种「不同的东西」编码后是同一个颜色。** 老 deck 的视觉区分 **100% 靠那 4% 存活的 1px 边框撑着**——边一掉，card / band / strip / 强调行看起来一模一样。

#### ① 面要活，色偏 ≥ 20

| 底色 | 色偏（R−B） | 结果 |
|---|---|---|
| `#fbf6f3`（暖） | 8 | ✗ 抹平 |
| `#f1f3f6`（冷蓝） | −5 | ✗ 抹平 |
| **`#f5dfe0`** | **21** | ✓ **保留 86%** |

#### ② 灰阶要活，相邻台阶 ≥ 6

浅色区的量化台阶实测（编码后 rgb）：

| 原始 | 原始对比 | 编码后 | 存活 |
|---|---|---|---|
| `#fafafa` | 4.4% | 247 | 到不了第一级 |
| `#f6f6f6` | 7.8% | 247 | **与上一行同色** |
| **`#f2f2f2`** | **11.2%** | **242** | **100%，正好落在台阶上** |
| `#eeeeee` | 14.5% | 242 | **塌进上一级** |
| **`#eaeaea`** | **17.7%** | **237** | ✓ |
| **`#e4e4e4`** | **22.4%** | **231** | ✓ |

**台阶是 247 / 242 / 237 / 231 / 226 / 222…… 每级约 5–6 个灰阶。**

### 面的阶梯（照这个用）

| 令牌 | 值 | 编码后 | 用途 |
|---|---|---|---|
| *(纸白)* | `#ffffff` | 255 | 页底 |
| **`--face`** | **`#f2f2f2`** | **242** | 分组 / 卡片 / code —— **最浅的活面** |
| **`--face-2`** | **`#eaeaea`** | **237** | 加重面：结论条、表头 |
| **`--face-3`** | **`#e4e4e4`** | **231** | 最高一级，慎用 |
| **`--accent-bg`** | **`#f5dfe0`** | — | 强调面（**靠色偏，不靠灰阶**） |

**三级封顶。** 再往下（`#dedede` = 226）只剩 5 个灰阶差，不可靠。

#### ③ 深色页的**每个面**都必须有对偶

浅面 `#f2f2f2` 在深底 `#12151a` 上是一块**亮斑**，不是「浅色分组」。
和 `--accent-d` 同构：每个面都要有深色版，由 `.slide.dark` 切换。

| 浅色 | 深色 | 用途 |
|---|---|---|
| `--face` `#f2f2f2` | `--face-d` `#1e232b` | 卡片 / 分组 / code |
| `--face-2` `#eaeaea` | `--face-2-d` `#252b34` | 结论条、表头 |
| `--face-3` `#e4e4e4` | `--face-3-d` `#2c333d` | 最高一级 |

> **漏掉这个是重建 Reviewer deck 时当场踩的**：`.card` 在深色页上变成亮斑，
> 而这在**浅色页的截图里完全看不出来**——只有翻到深色页才发现。

### 硬约束四：图片底色是**整份 deck** 的决定，不是逐页的决定

**逐页决定「这页有截图，所以这页做成深色」会产生「不规则的黑」，
看起来像两套 deck 拼起来。**

Reviewer deck 实测（8 页）：

| 页 | 有截图吗 | 底色 |
|---|---|---|
| p3 | 有（大的） | 深 |
| p4 | 有（两条） | 白 |
| p5 | 有 | 白 |
| p6 | 有（两张） | 深 |
| p7 | 有（一条） | 白 |

**五页有截图，只有两页是深的。** 这不是「两种底色混用」——
是**同一种情况用了两种处理**，而观众感觉到的就是「不协调」。

**两种一致的做法，二选一，不许混：**

| | 截图读起来像 | 代价 |
|---|---|---|
| **全白**（推荐） | 「这是一张贴在页面上的图」 | 页面里会有一批黑方块 |
| **全深** | 「这就是这一页本身」 | 整体偏重，`--accent-d` 要覆盖全篇 |

> **一致性是一眼能看到的品质，节奏感是主观的。**
> 而且 deck 要导出 PDF 发给别人看 —— 一致性比节奏重要。

**⚠️ 「深色版单看更好」是个陷阱。** 单独看 Reviewer deck 的 p3，
深色版确实更漂亮（终端截图融进页面，不像贴上去的图）。
但那是因为**你一次只看这一页** —— 翻完整本，两个不规则的黑才是真实体验。

### 硬约束五：`u = 28` 下截图**必须裁**

正文从 23px 涨到 28px 换来的是可读性，**代价全部落在截图上**。

一张 1400×769 的终端截图放全宽（1112px）要 **611px** 高，
而正文区只有 **324~420px**。不裁只有两个结局：**截图小到读不出字，或者溢出。**

| 截图原始宽高比 | 全宽（1112px）时的高度 | 放得下吗 |
|---|---|---|
| 1400×769（1.82） | **611px** | ✗ 差一倍 |
| 1400×337（4.15） | 268px | △ 只剩一条缝 |
| **1345×223（6.03）** | **184px** | ✓ |
| 1800×126（14.3） | 78px | ✓ |

**判据：宽高比 ≥ 5 才能放全宽；不够就裁到 4–5 行。**

> **裁哪几行是编辑判断，不是排版判断。**
> 那几行必须**自己构成一个论证**（前因 → 证据 → 结论），
> 不能只是「有信息的几行」。
>
> 反面教材：Reviewer deck 第 3 页原来放整张 11 行的评审输出，
> 缩到全宽后字高只剩 9px —— **证据读不出来，这页就废了**。
> 裁到「但 B1 说明一个问题 → 唯独纯读文档那节错了」这 4 行之后才成立。

> **⚠️ 禁用 `#fcfcfd` 这一档。** 它在 6 灰阶台阶之下，编码后会被**推到 247**：
> 比设计值更深，而且**和任何其他近白色都不可区分**。

### 所以 `--line` 是「完整简写」而不是颜色

```css
--line: 2px solid #b8b8b8;   /* 编码后 22.0%，纸白对比 27.8% */
```

代码里写 `border-bottom:var(--line)`，**宽度和颜色绑在一起**，不允许有人只拿它当颜色用。11 处旧写法 `1px solid var(--line)` 已全部换掉。

### 分隔线的三个备选（美学取舍，代码里用 #b8b8b8）

| 方案 | 编码后 | 观感 |
|---|---|---|
| **2px `#b8b8b8`（现用）** | 22.0% | 略重，像表格线。**存活余量 2.75×** |
| 2px `#c4c4c4` | 12.6% | 更淡更好看，但余量只有 1.6× |
| **不用线，只靠行距** | — | **最简约，而且零风险**（没有东西可以丢） |
| #f0f0f0 交替底带 | 4.3% | 太淡，不推荐 |

> 分隔线如果**不承载信息**（条目表的结构由编号和粗体关键词承担），那它消失也无所谓，可以用 1px 甚至不用。
> 如果**承载结构**（页眉线、页脚线、两栏中缝、节点框），就必须 ≥2px。

**实测值（白底 `#ffffff`）：**

| 令牌 | 值 | 对比度 | 结论 |
|---|---|---|---|
| `--ink` | `#101010` | 19.03:1 | ✓ |
| `--ink2` | `#454545` | 9.59:1 | ✓ |
| `--muted` | `#767676` | 4.54:1 | ✓ **最浅的合格灰** |
| `--line` | `2px #b8b8b8` | 2.02:1 | ✓ 屏幕共享下编码后 22.0% |
| `--accent` | `#a70e13` | 7.73:1 | ✓ 红色 |
| `--accent-bg` | `#f5dfe0` | 1.27:1 | ✓ 面状，存活率高 |

**实测值（深底 `#12151a`）：**

| 令牌 | 值 | 对比度 | 结论 |
|---|---|---|---|
| `--ink` | `#e9ecef` | 15.43:1 | ✓ |
| `--ink2` | `#b6bec9` | 9.76:1 | ✓ |
| `--muted` | `#8f9aa8` | 6.41:1 | ✓ |
| `--line` | `#343a44` | 1.60:1 | ✓ |
| `--accent` | `#ee4248` | 4.80:1 | ✓ 提亮版 |

### 三条实测得出的纪律

**① `--muted` 不能再用 `#9b9b9b`。**
它在白底上只有 **2.78:1**，连 3:1 都不到。把页脚、英文小注、注解放在这个灰上，投影时直接看不见。**两份已有 deck 都有这个问题。**

**② 深色页的强调色必须换值。**
红色 `#a70e13` 在白底上是 **7.73:1**（很宽裕），但在深底上只有 **2.37:1**——连图形都不够。深色页用提亮版 `#ee4248`（4.80:1）。

**③ 强调行只靠底色。**
红色压在浅红底上是 **6.08:1**，技术上允许再用红字。但不用——**一块底色已经把话说完了，再加红字是重复强调。**（之前用 `#e60012` 时红字只有 3.81:1，那时是硬约束；换成当前红色后变成了风格选择。）

### 强调色的使用纪律

**只允许四处**：① 小节标签 ② 条目编号 ③ 落点句左竖线 ④ 图上的箭头。
**用得越少，它才越有强调力。** 一页最多一处强调底色。

### 选哪个零件

清单在下面那张生成的表里 —— 这一段说的是**什么时候用哪个**，那是机械检查说不出的事。

**骨架（每一页都有，顺序固定）：**

| 零件 | 位置 | 什么时候写 |
|---|---|---|
| `.head` | 页眉容器 | 恒有。里面是 `.kicker` ＋ `.hline` |
| `.kicker` | 小节标签 | 写「§号 · 小节名」。**详略感由它承担**，页脚不重复 |
| `.hline` | 页眉线 | 恒有。结构性，恒 2px —— 这是全 deck 唯一还允许的线 |
| `.lead` | 导语 | 只有需要铺垫时写。**写了就和落点句抢地方**（260.1 vs 334.8） |
| `.body` | 正文区 | 恒有。唯一伸缩的块，**必须 `overflow:hidden`** |
| `.quote` | 落点句 | 有明确结论时写。目标是**一行说完**（多一行 −60.4px） |
| `.caveat` | 代价说明 | 结论有前提/代价时写。21px muted，不是正文 |
| `.cap` | 图注 | 有截图/表时写。16px muted，贴在图正下方 |
| `.foot` | 页脚 | 恒有。中 = deck 全名，右 = 页码。**讲者只在封面** |

**正文原型（一页选一种，别混）：**

| 你要说的东西 | 用 | 不用 |
|---|---|---|
| 并列条目，**「第几」本身有含义** | `.rows` | `.bullets` |
| 并列条目，**顺序不承载信息** | `.bullets` | `.rows` |
| 一句话一条的论点，要突出几个关键词 | `.args` | `.rows` |
| 两栏对照（A 对 B） | `.pair` | 两个 `.cards` |
| 三到四个并列概念，每个配一句话 | `.cards` | `.pair`（它只有两栏） |
| 有先后／有因果的几步 | `.flow` | `.bullets` |
| **会回到起点**的过程 | `.loop` | `.flow` |
| 一页只有一句结论，别的都多余 | `.band` | `.quote`（那是页脚位的） |
| 全页就是一页证据（截图/日志） | `.shot` | 硬塞进 `.cards` |

**页型（整页换骨架）：**

| 零件 | 什么时候用 |
|---|---|
| `.cover` | 首页。标题 + `.sub` + `.ctag`（讲者唯一出现的地方） |
| `.toc` ＋ `.ti` | **超过 3 个 section** 才值得单独一页，否则删掉 |
| `.sect` | 分章。`.snum` ＋ `.sline` ＋ `.sub`。**小节少就别用** |
| `.end` | 末页。`<section class="slide end">`，它自己不画东西，只换后代的样式 |

**变体（必须跟着基类写）：**

| 写法 | 什么时候用 |
|---|---|
| `.rows.tight` | 四条带小注的条目时。行距 0.44u → 0.24u，**每行省 11px** |
| `.args.tight` | 五条论点时。同上 |
| `.row.hi` | 整行强调。**只靠底色就够，不要再加红字** |
| `.card.acc` / `.band.acc` | 红色底。一页最多一块 —— 两块就没有重点了 |
| `.pill.dim` | 流程里弱化的节点 |
| `.slide.dark` | **整份 deck 的决定，不许逐页切**（§5 硬约束四） |

**复合零件的内部结构（子元素不能单独用）：**

| 复合件 | 内部 | 约束 |
|---|---|---|
| `.loop` | `.lrow`（一行）→ `.lnode`（节点，内含 `.ln` ＋ `.ls`）· `.larr`（正向箭头）· `.lback`（回环箭头）· `.lnote`（图下小注） | `.lnode` 宽 8u=224px → **最多 8 个中文字** |
| `.pair` | `.col`（一栏）→ `.lab`（栏标签）＋ `.val`（栏内容） | 只有两栏。三栏以上用 `.cards` |
| `.flow` | `.pill`（节点）· `.arw`（箭头） | 一页最多 4 个节点，再多就挤 |
| `.cards` | `.card`（卡片）→ 内含 `b`（编号）＋ `h3`（标题）＋ `p`（说明） | 3–4 张。两张用 `.pair` |
| `.toc` | `.ti`（一行）→ `.tn`（编号）＋ `.tt`（标题）＋ `.td`（一句说明） | — |
| `.sect` | `.snum`（大号章节号）· `.sline`（线）· `.sub`（一句说明） | — |

> **⚠️ `.tight` 不是万能的。** 带 `<small>` 的行**高在两行 `.k` 上，不在 `.v`** ——
> 一条 98.2px，四条就是 392.9px，而正文区最多 420.8px（不写落点句）。
> **所以删 `.v` 的字救不了页面，删一条才救得了。**

容量不是规定的，是 §4 的正文区高度除以行高算出来的。

**⚠️ 正文区高度取决于页面上还有没有别的元素。** `u=28px` 实测：

| 页面上有什么 | 正文区高度 |
|---|---|
| 只有正文 | 420.8px |
| 正文 + 落点句（无导语） | 334.8px |
| 正文 + 导语 + 落点句 | **260.1px** ← 最紧 |

行高（`u=28`、不用线）：

| 原型 | 单行高 | 420.8 放得下 | 334.8 | 260.1 |
|---|---|---|---|---|
| 编号条目表（含英文小注） | 86.2px | 4.8 → **4 行** | 3.8 → **3 行** | 3.0 → **3 行** |
| 编号条目表（无小注） | 65.6px | 6.4 → **6 行** | 5.1 → **5 行** | 3.9 → **3 行** |
| 三条论点 | 80.1px | 5.2 → **5 条** | 4.1 → **4 条** | 3.2 → **3 条** |
| 两栏对照 | — | 2 栏 | 2 栏 | 2 栏 |
| 循环图 | ≈280px | 1 组 | 1 组 | 1 组 |
| 截图区（`flex:1`） | — | 1 张 | 1 张 | 1 张 |

### ⚠️ 落点句每多一行，正文区少 **60.4px**

容量表里的「正文 + 落点句 = 334.8px」**前提是落点句只占一行**。

实测（Agent deck 的 p3 vs p4，都是「无导语 + 有落点句」）：

| 落点句 | 正文区 |
|---|---|
| **1 行**（「聊天机器人只有大脑。」） | **334.8px** |
| **2 行**（「聊天机器人不会失败后自愈，它只会道歉 —— 因为它没有眼睛。」） | **274.4px** |

**差 60.4px —— 正好一行落点句（`--fs-quote` 40px × 1.5 行高）。**

> **所以落点句写长了，等于偷偷把正文区砍掉一行的容量。**
> 落点句的目标长度是**一行说完**；两行不是「更完整」，是「多花 60px」。

### 导语和落点句只能二选一（`u=28` 的硬约束）

**导语 + 落点句 + 3 行条目表 = 放不下。** 实测模板改到 `u=28` 时，三个展示页当场溢出
（最少的一页是 −18.3px）。

两条路：

1. **删导语，保留落点句** —— 正文区 260.1 → 334.8px（+74.7px，多出一行）
2. **删落点句，保留导语** —— 但要问自己：这页的结论到底写在哪

> **优先保落点句。** 导语是铺垫，落点句是这页唯一要记住的东西。

**放不下就拆页，不要缩字号。** 字号是 §0 的场地决定的，不能为塞内容牺牲。

### 列宽是硬约束，不是建议

`.row` / `.arg` 的列宽是固定的 `u` 倍数，**内容超了就折行，折行就吃掉一整行的容量**。

| 列 | 宽度 | 能放多少 |
|---|---|---|
| `.row .n` 编号 | `1.52u` = 38px | 2 位数字 |
| `.row .k` 关键词 | `5.6u` = 140px | **最多 4 个中文字**（字号 `1.20u` = 30px） |
| `.row .k small` 英文小注 | 同上 | **最多 14 个 ASCII 字符** |

**实测踩过的坑**：demo 第一版关键词写成「正文 ≥ 25px」（2 中文 + 符号 + 4 ASCII），
四个关键词全部折行，行高从 77px 涨到 108.6px，四行表格从 308px 撑到 434.5px，余量只剩 17px。

**对策是把数字和限定条件移到 `.v` 栏**，关键词只留 4 字以内的名词：

| ✗ 会折行 | ✓ 不折行 |
|---|---|
| `正文 ≥ 25px` | `正文字号` → `.v` 写「≥ 25px，由窗口宽度反推」 |
| `底带优于细线` | `优先用面` → `.v` 写「底带存活率高 20 倍」 |
| `一页一结论`（5 字） | `结论唯一` → `.v` 写「落点句只写一句」 |

> **`check.py` 查得出溢出，但查不出“为什么行变高了”。** 余量异常时先看关键词有没有折行。

**`.loop .lnode` 也受同样的约束：** 宽 `8u` = 224px，`--fs-note` 23px 下一行
**最多 8 个中文字**。第 9 个字会单独掉到第二行变成**孤字**。

实测：Agent deck 原来写「用眼睛看改成了什么」（9 字）→ 最后那个「么」孤零零占了一行。
改成「看改成了什么样」（7 字）才对。

> **孤字没有机械检查。** `check.py` 量得到溢出，量得到余量，
> **但断行在哪里好看，只有人看得出。** 每改一次文字都该渲图看一眼。

## §7 · 纪律

1. **一页讲一件事。** 讲不清就拆页。
2. **每页一个落点句。** 它是这页唯一的结论，固定在骨架第 ⑤ 锚点。
3. **字号下限不可破。** 内容多了拆页，不是缩字。
4. **术语密度由受众决定，但专有名词保留英文原名。**

   | | |
   |---|---|
   | **该保留英文的** | 有正式名称的概念 —— `Agent Loop`、`context`、`checkpoint`、产品名 |
   | **不该硬塞英文的** | 你自己造的比喻（大脑 / 手 / 眼睛 / 记忆）—— 那是解释工具，不是术语 |

   **术语第一次出现：英文原词 + 一句人话。**

   > **不要因为「怕术语」就自造中文译名。**
   > 观众迟早会在别处看到英文原词 —— 自造译名等于**让他学两遍**：
   > 你的中文名，和他在工具里看到的英文词。
   >
   > 实测：「Agent Loop」原本被我写成「**圈**」。观众真到了别处只会看到 `loop`，
   > 那个「圈」他一个字也用不上。

   非技术受众仍然**零未解释的术语** —— 区别在于：术语照样出现，
   但每次出现都跟着一句人话。

5. **有代价才可信。** 讲优点必须带代价。
6. **一次按键＝一页。** 不做逐元素动画——投影现场不给你重播的机会。
7. **改文案时，代词必须仍有先行词。**

   **压行数时可以删修饰、删举例，但不能删主语。**
   删掉之后「它 / 这 / 那」会就近指代上一句 —— **意思可能整个反过来，
   而排版完全看不出来。**

   > **实测（连踩两次同一个坑）**：
   >
   > 原文「**聊天机器人**不会失败后自愈，**它**只会道歉 —— 因为**它**没有眼睛。」
   >
   > 为了把落点句从 2 行压到 1 行（2 行要吃掉 60.4px 正文区，见 §6），我删掉了前半句：
   >
   > 「**它**只会道歉 —— 因为**它**没有眼睛。」
   >
   > **「它」失去了先行词。** 这一页从头到尾在讲 Agent、图里还写着「看结果」——
   > 于是读者把「它」读成 Agent，**句子变成了「Agent 看不见结果」，和这一页在讲的事相反。**
   >
   > 第二次修的时候我只补了因果、没补主语，还是错的。
   >
   > **正确写法**：「**聊天机器人**没有这个 Loop —— **它**只会说抱歉。」
   >
   > **教训：为了排版动文案之后，必须重读一遍「读者会怎么理解」，
   > 而不是只检查「它还能不能放下」。** `check.py` 只量得到后者。

## §8 · 导出 PDF

### 先把「目的」和「手段」分开

| | 是什么 | 怎么查 |
|---|---|---|
| **目的** | 导出的 PDF 里 `/SMask` 和 `/Luminosity` 必须为 **0** | `check.py --pdf`（硬判据） |
| **手段** | 屏幕样式不用 `box-shadow` / `linear-gradient` | 静态检查（**代理指标**） |

**代理指标会错。** 曾经因为把 `@media print{ .shot{box-shadow:none!important} }` 数成违规，误判了唯一一份已经上过战场、验证干净的 PDF。**一个会误伤正确做法的门禁，比没有门禁更糟** —— 它会训练人忽略它的输出。

所以：屏幕样式里**可以**用阴影，只要 `@media print` 里关掉。`check.py` 现在会识别这个写法并放行。

### 两个都是真元凶，而且产生不同类型的掩码

对照实验（只恢复一项，其余不动）：

| 只恢复这一项 | `/SMask` | `/Luminosity` |
|---|---|---|
| 都不恢复 | 0 | 0 |
| 只恢复 `box-shadow` | **6** | **5** |
| 只恢复 `.hl` 的 `linear-gradient` | **4** | **0** |

```css
/* ✗ 会产生软掩码 */
.lift{box-shadow:0 16px 40px rgba(0,0,0,.35)}
.hl  {background:linear-gradient(transparent 58%, rgba(167,14,19,.3) 58%)}

/* ✓ 零掩码 */
.lift{border:1px solid var(--line)}          /* 或：屏幕留阴影，@media print 里 none */
.hl  {background-color:rgba(167,14,19,.3);background-repeat:no-repeat;
      background-size:100% 44%;background-position:0 92%}
```

### Type 3 字体：体积的真正来源

`PingFang SC` 在 Skia 下会退化成 **Type 3**（逐字绘图指令，**每页重复嵌一份**），而 `Georgia` 是正常的 CID TrueType。

实测：

| deck | 字体子集 | 其中 Type 3 | 体积 |
|---|---|---|---|
| template（7 页，零图片，纯文字） | 24 | 21 | **434 KB** |
| 一份真实 deck（8 页，7 张图） | 282 | 277 | 2.52 MB |

- **文字仍可提取** —— Type 3 没有破坏 ToUnicode，`pdftotext` 两份都能完整提出中文
- **代价是体积** —— Type 3 是矢量绘图指令，比字形子集大得多

**所以否决 Ghostscript 的理由要改。** 旧文档写它"破坏 ToUnicode"——**根因是 Type 3，不是 Ghostscript**；它处理正常的 CID TrueType 一般没这个问题。正确的结论是「**先让中文正常嵌入**」。

解法是换一个 Skia 能正常子集化的中文字体（思源黑体 / Noto Sans SC），但那需要 `@font-face` + base64 —— 和 §3.9 的单文件约束直接冲突。**这是个真实的权衡，尚未决定。**

### 导出命令

**不要用浏览器“打印 → 存储为 PDF”**，那会绕过 `@media print` 里的修复。

```bash
CH="/Applications/Google Chrome.app/Contents/MacOS/Google Chrome"
"$CH" --headless=new --disable-gpu --no-pdf-header-footer \
      --virtual-time-budget=6000 \
      --print-to-pdf="Deck.pdf" "file://$PWD/deck.html"
```

## §9 · 发布前自检

```bash
./scripts/check.py deck.html --pdf Deck.pdf
./scripts/check.py --self-test          # 反向用例：确认坏了的东西真的会被抓到
```

**自动查的：**

- 零外部引用
- `box-shadow` / `linear-gradient` —— 屏幕样式里判，但 `@media print` 里关掉的写法放行
- **逐页容量** —— 余量门槛 `1.92u`（导语一行），低于就报警；硬溢出报错
- **横向/纵向越界** —— 纵向比 `.body` 盒子，横向比幻灯片物理边缘（见 §4）
- PDF：`/SMask` `/Luminosity` 必须为 0；尺寸 960×540pt；字体子集数

**必须人眼过的：**

- [ ] 逐页看一遍，有没有视觉上的错位
- [ ] 退到最远座位，看最小的一行能不能读

### `--self-test`

`tests/` 下四个用例，改 `check.py` 后必须全过：

| 用例 | 期望 | 考的是 |
|---|---|---|
| `good.html` | 通过 | 不会误伤正常页 |
| `bad_A.html` | 报错 | 纵向溢出（条目表塞 7 行） |
| `bad_B.html` | 报错 | 横排两列都超量 |
| `bad_C.html` | 报错 | **单个 stretch 子项 + 文字溢出**（盒子等高，只看盒子测不到） |

### check.py 踩过的四个坑（都已处理，不要改回去）

1. **`getBoundingClientRect()` 返回缩放后的尺寸。** `#stage` 按视口缩放，不校正的话所有测量值都偏小。
2. **探针不能用 `requestAnimationFrame`。** 带大量 base64 图片的页面首帧可能晚于 `--dump-dom`，探针会静默不跑。改同步执行。
3. **溢出不能用「子元素高度累加」判。** 横排 flex 里并排的列会被加成 2 倍；更麻烦的是 `align-items:stretch` 把子项盒子拉成容器高后，**盒子不溢出、文字溢出到盒子外**，任何基于盒子的判据都测不到。要比几何位置，并用 `Range` 量文本节点。
4. **静态 grep 是代理指标。** 见 §8 开头。
