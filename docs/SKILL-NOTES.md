# SKILL-NOTES.md · 把 `_theme/` 做成 skill 的设计笔记

> **这是判断，不是规范。** 记在这里是因为它只活在对话里，对话会滚掉。
> 规范 → `RULES.md` · 操作 → `BUILD.md` · 静默失败 → `FAILURES.md`

---

## 1 · 判断：值得做，但现在不是时候

### 值得做的理由（不是"方便"，是更硬的东西）

大多数 skill 是"我喜欢这么干"——一条偏好，换个场合就不成立。这套不一样：

| | 理由 |
|---|---|
| **① 知识是非显然的** | 「1px 线在 H.264 下只剩 4%」，没人能凭直觉猜到。**再强的模型从零开始也会用 1px 线、也会用 `box-shadow`、也会用 PingFang。这不是审美，是编解码器的行为。** |
| **② 结论是可验证的** | 每条规则背后都有一次实测。不需要相信，跑一遍就知道 |
| **③ 已经有机械验收** | `check.py` 会把违规判成失败 —— **skill 里极少有这种东西** |

**第 ③ 点最关键。** 一份"请遵守这些规则"的 skill，在长对话里会被逐渐遗忘；
一份"结束前必须跑这条命令，不通过不算完"的 skill，不会。
**它让 skill 的正确性不依赖于 agent 听话。**

### 现在不做的理由

**① 规格 ≠ 产品。** 这套东西从没被用来真正交付过一份 deck。
skill 的本质是一句承诺——"照这个做，你会得到好结果"——而我们还没有资格承诺。

**② 形状取决于三个还不知道答案的问题：**

- **零件库到底缺什么** —— 现在 9 页全是**展示页**（存在的目的是把零件摆出来）。
  真 deck 要**说点什么**，而说话的时候才发现缺原型 / 零件凑不到一起 / 容量比以为的紧
- **工作流是 5 条命令还是 1 条** —— 现在是 5 条，埋着 3 个坑
- **内容层要不要写进去** —— 现在只活在两份 deck 的隐性习惯里

**③ 不可逆。** 写 `SKILL.md` 的那一刻等于宣布"这就是做法"。
可上个月还在改 `u`、这个月在改线宽、今天才定字体。**现在写，一个月后必然重写。**

### 但"等"是错的，正确的动作是"记"

现在有两个不对称：

> **规则全都记下来了（`RULES.md` / `PLAN.md`），过程没有。**
> "怎么跑"、"坏了会怎样"、"为什么当时这么判断" —— 只活在对话里。

而 **skill 大部分是过程**。所以先立三份 doc，就是本目录这三份。

## 2 · 入口：必须是显式的，不自动判断

**已拍板。理由值得记下来：**

**这套规范的前提很窄** —— 屏幕共享 · 对方窗口 900px · 中英混排 · 芯原品牌色。

**在前提之外，它不是中性的，它会主动害人：**

| 换掉的假设 | 会怎样 |
|---|---|
| 改成投影 | `u` 的推导是错的（投影时 `u` 由场地决定，不由窗口决定） |
| 改成纯英文会议 | 字体策略是错的（纯思源的前提是中英混排要齐平） |
| 用户其实要 `.pptx` | 交给他一个 HTML |

**一个只在窄条件下正确的东西，不该自动加载。**
自动加载意味着"匹配到『幻灯片』就上"，而失败的样子是**用户拿到一份看起来没问题、
实际前提全错的东西**。

### 所以描述里必须写清「不适用于」

- 要 `.pptx` / Google Slides 的
- 纯英文、面向英语观众的
- 投影仪现场演讲（不是屏幕共享）

## 3 · 将来 `SKILL.md` 的结构

### 分层：两层，不是一层

`RULES.md` 现在 30 KB。**每次开一份 deck 都加载 30 KB 是浪费**，而且噪音会稀释掉
真正重要的那几条。

```
slides/
  SKILL.md          ← 常驻。铁律 + 流程 + 速查表。目标 ≤ 200 行
  RULES.md          ← 按需。完整规范 + 推导 + 实测数据
  BUILD.md          ← 按需。操作
  FAILURES.md       ← 按需。静默失败清单 ★
  build.sh          ← 一条命令跑完 HTML→字体→检查→PDF→截图
  template.html     ← 无字体版（~28 KB，字体用时注入）
  check.py
  build_font.py
  tests/            ← 反向用例
```

### 关键判断：`RULES.md` 留完整的「为什么」，`SKILL.md` 只留一行版的

**光有"禁止 `box-shadow`"是不够的** —— agent 会觉得它更好看，然后"出于好意"违反。
它需要知道"会在 PDF 里生成软掩码，肉眼看不见但打印机和某些阅读器会露出灰底"。

> **一句 why 是绑定的，那张表不是。**

### 映射：`SKILL.md` 各节从哪来

| `SKILL.md` 的节 | 来源 |
|---|---|
| 什么时候用 / **不适用** | 本文 §2 + `PLAN.md §1 不目标` |
| 前提与重推（`u = 22400 / Sv`） | `RULES.md §2` |
| 铁律 N 条（每条一句 why） | `RULES.md §3–§8` 压缩 |
| 工作流五步 | `BUILD.md §1` |
| 速查：令牌表 · 原型清单 · 容量表 | `RULES.md §6` + `template.html` |
| **失败目录** | `FAILURES.md` 速查表 |
| 内容层 | 本文 §5（**现在还只是观察，没成文**） |

### 我认为最该单独成节的两块

**① 失败目录。** 这是 skill 里最值钱的内容，因为**它是下一个 agent 会犯的错**。
格式固定：

> **你做了什么** → **会发生什么** → **为什么屏幕上看不出来** → **怎么查**

右边那三个字是全部重点 —— 这些都是"错了但不报警"的错。
把它们列出来，等于给下一个 agent 装上一次性的经验。

**② 冻结线**（见下）

## 4 · 冻结线：什么能动，什么不能动

必须写死一条边界，否则 agent 会"顺手优化"。

| | |
|---|---|
| **令牌冻结** | `--u`、颜色、字体栈、间距、字号阶梯 —— **不许改** |
| **页面自由** | 用哪个原型、几页、文字怎么写 —— **随你** |
| **容量是硬墙** | 超了就删字 |

**一句话版本：「页面结构你可以加，令牌值不要动。」**

---

## 5 · 内容层：还只活在两份 deck 里的规矩

**这是目前最大的缺口。** 模板解决的是字号、容量、离线、PDF、字体。
它**完全不解决**：这页该说什么、几页、怎么排序、什么让一页值得看。

而做一份 deck，**难的是后半截**。

> **只装模板的 skill，产出会是「排版精良、什么也没说的 deck」。**
> 这个失败模式比"排版难看"更隐蔽 —— **因为它一眼看去是合格的。**

已经存在但没写下来的：

- **标题必须是可证伪的断言**，不是名词短语
  「细线会消失」✓ /「线的可见性」✗
- **一页一个论点**。能删掉的论点就是多余的
- **落点句 = 这页唯一要被记住的东西**。写不出落点句，说明这页没有论点
- **白页讲论点 / 深页放证据**，交替形成节奏
- **页数由时间定，不由内容定**（10 分钟 8 页）
- **溢出了就删字，不许缩字号** ★

**最后一条最容易被违反**，因为 agent 的本能是"帮用户保住内容"——
它会顺手把字号调小。**而那正是这套规范禁止的事。**

## 6 · 变成 skill 之前还差什么

按重要性排，**第 1 件不能跳过**。

### ① ✅ 冷启动测试（做完了 —— 结论在下面）

**原计划**是「拿 `为什么需要 Reviewer` 重建」。**实际做法更好**：把 `_theme/` 拷到
`/tmp/fresh`，开一个**全新的 pi 会话**，只说一句「用这里的东西做一份 deck」。

**结果：通过。** 53 次工具调用 · 10 页 · 全部机械检查通过 · 视觉也合格 · 没人提示它。

**三条「规范真的在起作用」的证据：**

- **最反本能的那条被主动遵守了。** 它自己的话：*"trim wording (**never shrink type**)"*。
  `SKILL-NOTES §5` 说这条最容易被违反 —— 而 agent 的天性是把字号调小帮你保住内容。
- **事实是准的**：它去读了 pi 的 README 核对（`-nc`、`createAgentSession()` 都是真的）。
- **8 个论点页标题全是可证伪断言**，7 页有落点句，自己发现并修掉两处折行孤字。

**它卡住的地方 —— 这才是测试的价值：**

**★ 工具链缺「写页」这一环。** 它自己发明了「stage 文件 + 切片脚本」，
**四个回合里把同一段 Python 重写了四遍**（见 `FAILURES F8`）。
你给了起手（`newdeck.py`）、构建（`build.sh`）、验收（`check.py`）—— 唯独没给写页。

> **→ 做成 `setpages.py` 了。** 抽出／贴回，**边界以外逐字节不动**，写盘前自检五项。

**零件库有隐形零件**：`RULES` 点名 22 个类，CSS 里有 **66** 个。
`.rows.tight` 定义了但 12 页里一次没用；`.caveat` 用了但 RULES 没提。
新 deck 两个都用了 —— **但它是从 CSS 里翻出来的**，不是从清单或示范页。

**「太空」没有任何规则管**：`check.py` 只拦「装不下」，不拦「太松」。
模板自己就有 +148.8px 的页，新 deck 学样做出了 +172px 的页（见 `FAILURES F9`）。

**⚠️ 这次测试有一点泄漏**：它读到了 `SKILL-NOTES.md §5`（那六条内容规则）。
那份文档不会进 skill —— 除非按计划把它升格成规范（就是本节的 ⑤）。

**这是唯一能暴露「零件库缺什么」的方法。**

建议**拿 `为什么需要 Reviewer` 重建**。它是个完美的验收样本：

- **你已经知道它该说什么** —— 所以过程中碰到的任何困难，都是**模板的问题**，不是内容的问题

### ② ✅ 工作流：`build.sh` 一条命令 + `setpages.py` 一条命令

**`build.sh`**：依次跑字体 → PDF → 验收，任一步失败即停；`/tmp/slidenv` 丢了会自动重建。
起因是「改文字忘了重跑 `build_font.py`」**一个会话里踩了三次**，而后果完全静默。

**`setpages.py`**（冷启动测试后补的）：页面抽出／贴回，**边界以外逐字节不动**。
起因见 ① —— agent 会自己发明切片脚本，而那段脚本锚点漂移是静默吞内容的。

### ②b ✅ 零件清单要自动化

（见 ① 的发现：CSS 里 66 个类，RULES 只点名 22 个。）

**手写的零件清单一定会漂移** —— `.rows.tight` 定义了没人用，`.caveat` 用了没人写。
清单应该从 `template.html` 的 CSS **生成**，而不是手维护。

<details><summary>② 的原始说明（留档）</summary>



现在跑一份 deck 是 5 条命令，埋着 3 个坑：Chrome 的 headless flag、
**截图必须 `1280,720` 不是 `1280,807`**、**改完文字必须重跑 `build_font.py`**。

**这三个坑现在只存在于对话记录里，不在仓库里。**
skill 要能用，必须是"跑这条命令"，不是"记住这些 flag"。

</details>

### ③ `check.py` 补上现在查不到的四条规则

**规则靠"记住"是迟早会失效的。** 现在查不出来：

- 线宽（≥2px）
- 颜色对比度（正文 ≥ 4.5:1）
- 列宽（`.row .k` 最多 4 个中文字）
- 内容质量（有没有论点、有没有落点句）

### ④ 无字体版 `template.html`

skill 里放 28 KB 的版本，字体用时注入。
**顺带保证了一件事：每次都必须跑 `build_font.py`** —— 因为没有别的选择。

### ⑤ 内容层成文

本文 §5 那六条，从"观察"升格成"规范"。

### ⑥ 拆规范两层

`SKILL.md`（常驻）+ `RULES.md`（按需）。

**⚠️ 注意重复风险**：同一条规则会出现在两处，会漂移。
约定：**`RULES.md` 是唯一真相源，`SKILL.md` 是摘要。** 改规则先改 `RULES.md`。

## 7 · 还没想清楚的

- **要不要带上已完成的两份 deck 当范例？** 好处是有真实样本；
  坏处是它们不在新模板上，会示范过时的做法
- **`build.sh` 要不要管截图？** 截图是"看效果"用的，不是交付物
- **skill 的形态**：Claude Code / Codex / 两边都要 —— 形态不同，②怎么写不一样
- **多语言**：现在中英混排写死。要支持纯中文 / 纯英文吗？
